# 规则编写规范

本目录按“规则族 / 单条规则”组织。每条规则既是一个**审查单元**，也是一个**写作约束单元**。

## 一条规则必须同时服务两个阶段

### 写作阶段

AI 应能从规则中得到明确的前置约束，例如：

- 不要生成什么；
- 应优先使用什么；
- 哪些称谓、编号或版式必须统一；
- 哪类表达应在起草阶段直接避免。

### 审查阶段

AI 应能从规则中得到明确的验证方法，例如：

- 检查哪些关键词；
- 检查哪些结构或版式；
- 哪些情况必须结合上下文判断；
- 发现问题后如何修改。

因此，规则不应只是“问题描述”，还应形成完整的“预防—发现—修正—例外”闭环。

## 新反馈录入前必须去重

新增规则前，先读取 `catalog/rules.yaml` 并比较 `dedup_signature`。

候选问题按以下方式处理：

- **DUPLICATE**：已有规则完整覆盖，不录入；
- **EXTENSION**：已有规则可覆盖，补充示例或检测线索；
- **NEW**：独立问题机制，创建新规则；
- **CONFLICT**：与已有规则冲突，不自动覆盖，人工确认。

详细流程见 `workflows/ingest-feedback.md`。

## 单条规则建议结构

```markdown
# DR-XXX-000 规则标题

- 状态：active
- 严重度：high / medium / low
- 适用：技术方案 / 标书 / 合同 / …
- 规则类型：版式 / 文控 / 术语 / 语态 / 编号 / 责任表达 / …

## 去重签名
描述底层失败模式。

## 写作前置约束
描述写新文档时如何提前避免。

## 标准问题描述
用正式、可复用的语言描述问题。

## 为什么是问题
说明风险和影响。

## 判定标准
给出可执行条件。

## 反例
至少 2 个。

## 推荐表达 / 处理
至少 2 个。

## 检查方法
说明人工或 AI 如何发现。

## 与已有规则的关系
说明相近规则及差异。

## 例外
说明不应机械套用的场景。
```

## 编写要求

1. 规则描述必须可跨项目复用，不依赖某个具体客户或项目背景。
2. 反例可以来自真实文档，但进入仓库前应尽量去标识化。
3. “反例”用于识别模式，不代表所有包含某个词的句子都错误。
4. 推荐表达应优先给出可直接替换的正式文本。
5. 对合同、招标、法规、安全等必须明确边界的场景，应保留必要的否定式约束，不做绝对化禁用。
6. 每条规则应在 `catalog/rules.yaml` 登记，并至少具备：
   - `dedup_signature`
   - `authoring_guard`
   - `review_check`
7. 同一个底层问题不得仅因出现位置、词语或文档不同而重复建规则。
8. 新规则如果不能清楚说明“为什么现有规则无法覆盖”，通常不应新建。

## 规则生命周期

- `active`：当前有效；
- `deprecated`：不再推荐使用，但保留历史；
- `superseded`：已被其他规则替代。

除非确认是错误文件，否则不要通过删除规则来处理语义演进。
