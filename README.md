# Doc_Rule

面向技术文档、技术方案、标书、合同及其他正式交付文件的**反例规则库**。

本仓库不提供通用写作模板，而是持续记录在真实文档编写过程中发现的“不应出现的问题”，将其整理为可复用、可检索、可供 AI 直接引用的规则。目标是在文档**编写阶段主动规避**，并在**审查阶段系统检查**同类问题。

## 核心原则

1. **以反例驱动规则**：每条规则从具体错误表现出发，给出标准化问题描述、风险、检测线索、反例与推荐改写。
2. **面向正式交付场景**：默认假设文档将直接提交甲方、招标人、评审专家或合同相对方，而不是内部草稿、会议材料或编制说明。
3. **规则可被 AI 消费**：规则同时提供人类可读 Markdown 与机器可读索引，便于生成式 AI、审查脚本或文档工作流引用。
4. **强调“成品文档视角”**：正式文件只呈现最终方案、正式依据、职责分工和交付内容，不暴露内部生成过程、迭代过程、内部编码或供应商自我保护式话术。
5. **边界应专业表达**：必要的责任边界可以保留，但优先采用职责分工、能力范围和实施条件的正向表达；合同或招标文件明确要求的除外。

## AI 使用方式

### 编写前

AI 应先读取 `catalog/rules.yaml`，筛选适用于当前文档类型的规则，再开展起草。不得把规则理解为简单的关键词替换，而应理解其背后的正式文档语境。

### 编写后

至少完成一次“正式交付审查”：

- 检查是否存在内部编辑痕迹、提示框、高亮、批注式说明；
- 检查页眉、页脚、标题、修订信息是否暴露内部迭代过程；
- 检查项目名称、主体称谓、编号体系是否正式且全文一致；
- 检查是否出现“本方案用于”“本文介绍”等编制者自述；
- 检查图表附近是否混入内部资料来源或编制过程说明；
- 检查是否大量使用“不负责、不包含、仅用于、不作为”等防御性表达；
- 检查职责边界是否可以改写为“谁负责什么、系统实现什么、如何协同”。

可直接使用 `prompts/formal-document-review.md` 作为审查提示。

## 规则编号

- `DR`：Document Rule
- `FRM`：Formal Delivery / 正式对外交付
- 三位数字：规则序号

例如：`DR-FRM-007` 表示“正式交付类第 7 条规则”。

## 适用范围

当前首批规则主要适用于：

- 技术方案
- 投标技术文件 / 标书
- 项目建议书
- 实施方案
- 正式汇报材料
- 合同技术附件
- 验收方案及交付文档

后续可按实际反例继续扩展合同条款、投标响应、技术参数、排版、数据一致性、接口描述、验收指标等规则族。

## 数据使用说明

仓库中的示例应尽量做去标识化处理。反例用于描述错误模式，不代表任何特定客户、项目或组织的实际立场。
