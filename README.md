# Doc_Rule

面向技术文档、技术方案、标书、合同及其他正式交付文件的**反例驱动写作规范库**。

本仓库不是单纯的问题清单，也不是只用于“完稿检查”的规则集。它承担两个长期角色：

1. **反馈沉淀库**：从真实文档、截图和项目反馈中提取反例，语义去重后形成稳定规则；
2. **写作前置规范**：AI 在编写新文档时主动加载规则，在起草阶段直接避开已知问题，并在完稿后再次验证。

目标是形成一个持续演进的闭环：

```text
真实文档 / 用户反馈
        ↓
   提取候选问题
        ↓
     语义去重
   ↙      ↓      ↘
重复    扩展已有    新规则
不录入   规则        入库
        ↓
   形成稳定规则库
        ↓
AI 编写新文档时前置引用
        ↓
完稿后按相同规则自检
        ↓
新的真实反馈继续沉淀
```

---

## Agent 如何使用本仓库

**只要 Agent 能读取本仓库，就应先读取根目录的 `AGENTS.md`。**

`AGENTS.md` 已定义自动任务路由，Agent 不需要用户额外提供专门提示词。它会根据当前任务自动进入以下模式：

- **AUTHOR**：编写、起草、改写、完善正式文件；
- **REVIEW**：检查、审查、比较现有文档；
- **LEARN**：从真实反馈中沉淀规则；
- **MAINTAIN**：维护规则库结构和生命周期。

机器可读的任务路由同时位于：

`catalog/task-profiles.yaml`

## 核心原则

1. **以反例驱动规则**  
   每条规则从真实错误表现出发，抽象为可跨项目复用的问题机制。

2. **先去重，后录入**  
   新反馈必须先与已有规则做语义比较。相同问题不重复建规则；新表现优先扩展已有规则。

3. **规则既用于审查，也用于写作**  
   每条规则都应回答：
   - 写作时怎么提前避免；
   - 审查时怎么发现；
   - 发现后怎么改；
   - 什么情况下不应机械套用。

4. **默认按正式对外交付标准处理**  
   除非明确说明为内部草稿，否则假设文件将直接提交甲方、招标人、评审专家、合同相对方或最终使用部门。

5. **只呈现最终成品，不暴露内部过程**  
   正式文件不应泄露内部迭代、草稿状态、内部编号、内部素材整理过程或供应商自我保护式话术。

6. **边界要专业表达，而不是弱化边界**  
   合同、安全、招标等必要边界应保留，但优先采用职责分工、能力范围和实施条件的正向表达。

## 反馈沉淀规则

当用户提供文档、截图或新问题时，Agent 应先把候选问题归为以下四类：

### DUPLICATE

已有规则已经完整覆盖。

**处理：不录入，不修改。**

### EXTENSION

底层问题相同，但增加了新的典型表现、检测线索、适用文档类型或更好的示例。

**处理：更新已有规则，不新建同义规则。**

### NEW

具有独立问题机制，无法合理归入现有规则。

**处理：创建新规则，并更新索引。**

### CONFLICT

新反馈与已有规则相冲突。

**处理：不自动覆盖，先澄清适用边界或请求人工确认。**

详细流程见：

`workflows/ingest-feedback.md`

## 写新文档时的使用方式

AI 不应“先生成，再拿本仓库纠错”。

正确方式是：

1. 识别当前文档类型；
2. 读取 `catalog/rules.yaml`；
3. 按 `applies_to`、`severity`、`category` 筛选规则；
4. 将每条适用规则的 `authoring_guard` 转换为前置写作约束；
5. 起草正式文档；
6. 完稿后按 `review_check` 做一次独立验证并直接修正；
7. 向用户交付成品。

详细流程见：

`workflows/author-document.md`

## 审查现有文档时的使用方式

审查时不能只做关键词扫描。必须结合上下文判断：

- 这是内部草稿痕迹，还是正式文控要求？
- 这是防御性免责话术，还是合同必须排除项？
- 这是内部自创编号，还是甲方正式需求编号？
- 这是内部素材来源说明，还是必须保留的正式引用？

详细流程见：

`workflows/review-document.md`

## 机器可读规则索引

`catalog/rules.yaml` 不只是目录，目前每条规则包含：

- `id`
- `title`
- `status`
- `category`
- `severity`
- `applies_to`
- `file`
- `dedup_signature`：用于判断新反馈是否重复
- `authoring_guard`：用于写作阶段提前规避
- `review_check`：用于完稿或现有文档审查
- `detection_hints`：辅助定位候选问题

这样 Agent 不需要先加载全部 Markdown，即可先做任务路由、规则筛选和去重候选搜索。

## 规则编号

- `DR`：Document Rule
- `FRM`：Formal Delivery / 正式对外交付
- 三位数字：规则序号

例如：

`DR-FRM-007` = 正式对外交付类第 7 条规则。

后续可扩展新的规则族，例如：

- `BID`：投标专项
- `CTR`：合同专项
- `TEC`：技术内容与工程表达
- `FMT`：版式与排版
- `DAT`：数据、参数与一致性
- `ACC`：验收与交付

具体是否拆分，以实际反例数量和独立问题机制为准，不提前制造分类。

## 当前适用范围

当前首批规则主要覆盖：

- 技术方案
- 投标技术文件 / 标书
- 项目建议书
- 实施方案
- 正式汇报材料
- 合同技术附件
- 验收方案及交付文档

后续通过真实反例继续扩展。

---

## 数据与隐私

仓库中的示例应尽量去标识化。

反例用于描述错误模式，不应公开真实客户名称、敏感项目编号、个人信息、未公开业务数据或其他没有必要进入规则库的信息。

## 给 AI 的最简入口

如果一个 AI / Agent 只读取一个文件，应读取：

`AGENTS.md`

如果需要机器化筛选规则，再读取：

`catalog/rules.yaml`

如果需要判断当前任务属于写作、审查还是反馈沉淀，再读取：

`catalog/task-profiles.yaml`

在正常情况下，**用户不需要再额外告诉 Agent“请引用本仓库作为写作规范”**；只要 Agent 已被要求使用或能访问本仓库，就应自动执行上述流程。
