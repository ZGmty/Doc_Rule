# 反馈沉淀工作流

本流程用于：用户提供真实文档、截图或问题描述，希望 Agent 从中学习并更新 `Doc_Rule`。

## 目标

把“某个具体文档的问题”转化为“可跨项目复用的规则”，同时避免规则库重复膨胀。

## 执行步骤

### 1. 提取候选问题

对输入材料逐项识别：

- 版式与文控问题；
- 项目名称与主体称谓问题；
- 语态与措辞问题；
- 编号与表格问题；
- 图表与资料来源问题；
- 责任边界与免责式表达问题；
- 其他会导致正式文件显得像草稿、内部稿、AI 稿的问题。

每个候选问题先形成一句**抽象的问题定义**，不要一开始就按原句创建规则。

### 2. 去标识化

进入规则库前应去除：

- 真实客户名称；
- 未公开项目编号；
- 敏感日期、设备编号；
- 内部人员信息；
- 其他不适合进入公开规则库的内容。

保留“错误模式”，不保留不必要的业务秘密。

### 3. 搜索现有规则

先读取 `catalog/rules.yaml`，使用：

- title；
- detection_hints；
- applies_to；
- category；

筛选最相近候选规则，再读取这些规则全文。

### 4. 做语义去重

对每个候选问题判断：

- **DUPLICATE**：已有规则已完整覆盖；
- **EXTENSION**：已有规则可覆盖，但值得增加新示例/检测线索；
- **NEW**：具有独立问题机制，需要新规则；
- **CONFLICT**：与现有规则冲突，需要人工确认。

判断依据是“问题机制 + 风险 + 修正原则”，不是表面关键词。

### 5. 处理结果

#### DUPLICATE

不新增，不修改。

#### EXTENSION

更新已有规则：
- 补充新反例；
- 补充推荐表达；
- 补充 detection_hints；
- 必要时补充 applies_to 或例外。

同时更新 `catalog/rules.yaml`（若索引字段发生变化）。

#### NEW

按 `rules/_template.md` 创建新规则，并同步更新：
- `catalog/rules.yaml`；
- 必要时 taxonomy / schema；
- README 仅在结构发生变化时更新。

#### CONFLICT

不自动覆盖。记录冲突点并要求人工确认。

### 6. 最终核对

提交前检查：

- 是否出现同义规则；
- ID 是否唯一；
- catalog 路径是否正确；
- 示例是否去标识化；
- 规则是否同时适合“写作预防”和“完稿审查”；
- 是否至少有 2 个反例和 2 个推荐处理方式。

## 推荐输出

反馈沉淀完成后，向用户说明：

- 新增了哪些规则；
- 哪些问题判定为重复而未新增；
- 哪些仅扩展了已有规则；
- 是否存在需要人工决策的冲突。

不需要把全部内部去重思考过程逐字展开。
